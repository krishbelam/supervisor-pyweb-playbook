Supervisor playbook for Python web apps

Supervisor keeps any long-running command alive, so this works for Django, Flask or FastAPI behind nginx, with an optional React frontend. Pick your framework below, fill in your details, and every snippet adapts. Tick off steps as you go and copy any command with one click.

Install supervisor and make sure it runs
sudo apt update
sudo apt install supervisor -y
sudo systemctl enable --now supervisor
sudo systemctl status supervisor

supervisord is the daemon. supervisorctl is the CLI you use to talk to it. Both need root (or a user in the socket’s group) to work.

Put each config in /etc/supervisor/conf.d/
sudo nano /etc/supervisor/conf.d/nginx.conf
sudo nano /etc/supervisor/conf.d/gunicorn.conf
sudo nano /etc/supervisor/conf.d/react.conf

The main file /etc/supervisor/supervisord.conf ends with an [include] block that loads /etc/supervisor/conf.d/*.conf. Files must end in .conf or they are ignored. One file can hold several [program:x] sections, but one file per program is easier to manage.

Paste the exact contents from the “Configs” tab, or use the suggested versions there.
Stop the systemd nginx so supervisor can own port 80
sudo nginx -t                      # validate your site config first
sudo systemctl stop nginx
sudo systemctl disable nginx       # stops it returning on reboot
sudo ss -tlnp | grep -E ':80|:443' # should be empty now
If you skip this, supervisor’s nginx fails with “address already in use” and keeps retrying until it hits startretries.
Make sure log files and the app’s prerequisites exist
ls {{VENV}}/bin/gunicorn
which serve                         # React needs the full path, see Configs
sudo touch /var/log/{{APP}}.stdout.log /var/log/{{APP}}.stderr.log

Supervisor creates log files itself, but it fails to start a program if the log directory doesn’t exist or isn’t writable.

Tell supervisor to read the new files
sudo supervisorctl reread    # lists new/changed/removed groups, changes nothing
sudo supervisorctl update    # applies the changes and starts autostart programs

Expect output like nginx: available then nginx: added process group. Use reread + update whenever you edit a .conf. Only the programs whose config changed get restarted.

Check status
sudo supervisorctl status

You should see RUNNING for all three. BACKOFF or FATAL means the command exits right after start. Read the stderr log (see Commands tab) for the reason.

Test the whole chain
ls -l {{SOCK}}                                  # gunicorn socket exists
curl --unix-socket {{SOCK}} http://localhost/   # talks to Django directly
curl -I http://localhost                              # through nginx

Your nginx site config should proxy to the socket:

location / {
    proxy_pass http://unix:{{SOCK}};
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}

Pick a file, then switch between a basic version and a suggested one. Suggestions are optional; the basic versions work as is, apart from the React serve path issue.


How supervisor names your processes

Because process_name uses %(process_num)02d, supervisor makes a group named after the program and a process inside it. This is what you type in supervisorctl.

ProgramProcess nameRestart it with
nginxnginx:nginx_00supervisorctl restart nginx:*
gunicorngunicorn:gunicorn_00supervisorctl restart gunicorn:*
react_appreact_app (your process_name line is commented out)supervisorctl restart react_app
Using group:* works for every program, with or without process_name, so it is the safest habit.

Backend code changed

cd {{BE}}
source {{VENV}}/bin/activate
pip install -r requirements.txt     # if dependencies changed
python manage.py migrate            # Django only
python manage.py collectstatic --noinput   # Django only
sudo supervisorctl restart gunicorn:*
Your gunicorn uses --preload, so the app is imported once in the master process. A HUP reload will not pick up new code. Do a full restart.

React app rebuilt

cd {{FE}}
npm run build
sudo supervisorctl restart react_app

serve reads files from disk, so often a rebuild alone is enough. Restart if the browser still shows the old bundle after a hard refresh.

Nginx site config changed

sudo nginx -t && sudo supervisorctl signal HUP nginx:*

HUP makes nginx reload its config gracefully with no dropped connections. This is the equivalent of nginx -s reload, and it keeps the process under supervisor’s control.

A supervisor .conf file changed

sudo supervisorctl reread
sudo supervisorctl update

A plain restart does not re-read the config file. Always run reread + update after editing it.

Something is stuck in FATAL or BACKOFF

sudo supervisorctl tail -f gunicorn:* stderr
sudo supervisorctl tail gunicorn:* stdout
sudo tail -n 50 /var/log/{{APP}}.stderr.log

Run the same command by hand as the same user to see the real error, for example cd {{BE}} && {{VENV}}/bin/gunicorn {{WSGI}}.

Supervisor manages processes on one machine. Whether that’s enough depends on how many services you run and where.

Good fit

  • One server or VM running a handful of services behind nginx.
  • Side projects, internal tools, staging boxes and small production apps.
  • Background workers (Celery, queue consumers) next to a web app.

Microservices: where you outgrow it

  • Roughly ten or more services, or services spread over several machines.
  • You need scaling across hosts, health-based routing, service discovery or rolling deploys. Supervisor has none of these.
  • Each service has its own dependencies, release cycle or team. Containers plus an orchestrator fit better.
  • Lighter single-host alternatives: systemd units (often the better default on a modern distro) or Docker Compose.

Running in Kubernetes: don’t use supervisor

Kubernetes already restarts, probes and scales your processes, and the convention is one process per container. Supervisor inside a pod hides a dead child process from the kubelet: the container looks healthy while the app is down, so probes, restarts and alerts stop telling the truth.

Carrying your Gunicorn setup into a container

CMD exec gunicorn --bind 0.0.0.0:8000 --worker-tmp-dir /dev/shm {{WORKER}} {{WSGI}}
  • Bind to a TCP port, not a unix socket. A Service routes over TCP.
  • exec makes Gunicorn PID 1, so Kubernetes’ SIGTERM reaches it and shutdown is graceful.
  • --worker-tmp-dir /dev/shm avoids heartbeat stalls on container filesystems.
The one case for several processes in a pod is a sidecar, such as nginx or a log shipper beside your app. Run those as separate containers in the same pod, not under supervisor.

For anyone who tried this out and wants a clean exit. Pick how far to go, then work down the list.

Stop the programs
sudo supervisorctl stop nginx:* gunicorn:* react_app
sudo supervisorctl status    # all should say STOPPED
Delete the config files
sudo rm /etc/supervisor/conf.d/nginx.conf /etc/supervisor/conf.d/gunicorn.conf /etc/supervisor/conf.d/react.conf
sudo supervisorctl reread
sudo supervisorctl update
Don’t skip this. A leftover .conf brings the program back on the next reboot. update should print “removed process group” for each one.
Remove logs and the socket
sudo rm -f /var/log/{{APP}}.stdout.log* /var/log/{{APP}}.stderr.log*
sudo rm -f /var/log/{{APP}}_react.*
sudo rm -f /var/log/supervisor/nginx_*
sudo rm -f {{SOCK}}
Give nginx back to systemd, or remove it

Confirm nothing holds port 80, then pick one:

sudo ss -tlnp | grep ":80"

# Option A: go back to the normal nginx service
sudo systemctl enable --now nginx

# Option B: remove nginx completely
sudo apt purge nginx nginx-common -y
sudo apt autoremove -y
Option B deletes /etc/nginx, including your site configs. Copy them somewhere first.
Remove the global React server
sudo npm uninstall -g serve

Skip this if you installed serve for other projects too.

Uninstall supervisor itself
This removes supervisor for every project on this machine, including configs you didn’t create here.
sudo systemctl stop supervisor
sudo systemctl disable supervisor
sudo apt purge supervisor -y
sudo apt autoremove -y
sudo rm -rf /etc/supervisor /var/log/supervisor
Optional: delete virtualenv and build output

Your source code stays untouched. Only do this if you won’t need these again.

rm -rf {{VENV}}
rm -rf {{FE}}/build {{FE}}/node_modules
Verify it’s clean
ps aux | grep -E "gunicorn|nginx|serve" | grep -v grep
sudo ss -tlnp | grep -E ":80|:{{PORT}}"
ls /etc/supervisor/conf.d/
sudo supervisorctl status    # with “Remove everything” this command no longer exists

No leftover processes, nothing on those ports, and no project .conf files means you’re done.
